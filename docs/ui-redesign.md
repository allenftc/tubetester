# Tube Tester Control UI Redesign Specification

## 1. Decision and scope

The first implementation should replace the standard-library HTTP control server with **aiohttp**, using HTTP for commands and initial snapshots and one WebSocket for live status and console events. This is an intentional framework migration: the current [`ThreadingHTTPServer`](../controller/web/server.py:80) cannot provide the requested WebSocket stream without implementing the protocol manually.

First-release scope includes:

- a responsive, three-region control surface;
- background workflow execution;
- cooperative pause, resume, and stop;
- a live rack/tube model;
- QR decoding integration with per-tube outcomes;
- a bounded, structured console event stream;
- Klipper/Moonraker connection and printer state;
- static HTML, CSS, and JavaScript assets outside the Python server module.

The UI must not manufacture capabilities. The current QR class is only an interface that raises [`NotImplementedError`](../controller/vision/qr_decoder.py:16), current workflow execution is synchronous in the request handler at [`_execute_workflow()`](../controller/web/server.py:90), and current Klipper macro configuration defines only a dry-run placeholder in [`scan.cfg`](../klipper/macros/scan.cfg:4). Code mode must implement or explicitly surface these prerequisites as unavailable rather than reporting false success.

## 2. Current implementation inventory and problems

### 2.1 Existing browser and API behavior

The entire browser application is generated by [`_render_index()`](../controller/web/server.py:148): HTML, CSS, and JavaScript share one Python formatted string. The server exposes:

| Method | Current path | Current behavior | Redesign disposition |
|---|---|---|---|
| GET | `/` | Renders inline page at [`server.py:21`](../controller/web/server.py:21) | Keep path; serve a template/static HTML file |
| GET | `/api/status` | Calls Moonraker server/printer info and returns the full workflow plan at [`server.py:24`](../controller/web/server.py:24) | Replace payload with normalized snapshot contract |
| POST | `/api/home` | Sends `G28` synchronously at [`server.py:36`](../controller/web/server.py:36) | Keep, normalize response, reject while unsafe/busy |
| POST | `/api/dry-run` | Returns every plan step at [`server.py:39`](../controller/web/server.py:39) | Keep, but summarize in UI and do not write to the console |
| POST | `/api/run-workflow` | Executes every Moonraker request before responding at [`server.py:42`](../controller/web/server.py:42) | Replace with nonblocking start action |
| POST | `/api/gcode` | Proxies arbitrary script at [`server.py:45`](../controller/web/server.py:45) | Keep with validation and structured event generation |

There is no polling loop after initial load, no WebSocket, no server-sent event stream, and no browser-side state model. [`refreshStatus()`](../controller/web/server.py:200) is called once at [`server.py:208`](../controller/web/server.py:208), unless the user manually presses Refresh Status.

### 2.2 Why the current UI becomes unreadable

1. Every action response replaces a single raw status element with indented JSON in [`post()`](../controller/web/server.py:192). A workflow response includes each step, generated command, and complete Moonraker response at [`server.py:134`](../controller/web/server.py:134). With a 6 × 12 rack from [`rack.json`](../calibration/rack.json:6) and 13 yaw positions from [`yaw.json`](../calibration/yaw.json:2), the plan contains 1,153 steps: one home plus 72 tubes times 16 operations. Its response can therefore occupy thousands of lines.
2. The status endpoint embeds the same full plan on every request at [`server.py:29`](../controller/web/server.py:29), even though rack geometry and plan structure are effectively static.
3. Workflow state and machine diagnostics are mixed in one [`pre`](../controller/web/server.py:188). There is no distinction among current step, tube result, command echo, informational response, warning, or error.
4. The workflow preview renders all steps as an unbounded list at [`server.py:149`](../controller/web/server.py:149) and [`server.py:184`](../controller/web/server.py:184), repeating details that should be represented by progress, phase, and rack cells.
5. The four control buttons at [`server.py:174`](../controller/web/server.py:174) have short labels but no descriptions, tooltips, disabled/busy states, confirmation rules, or outcome feedback separate from the raw dump.
6. Generic green styling at [`server.py:162`](../controller/web/server.py:162) gives Home, Dry Run, Run Workflow, Refresh, and Send G-code the same visual weight despite different risk.
7. Workflow execution blocks the POST handler at [`server.py:97`](../controller/web/server.py:97). There is no runtime object recording a current step, no cancellation token, no pause gate, and no per-tube result state.
8. The state machine defines a static plan, not runtime state. [`WorkflowPhase`](../controller/workflow/state_machine.py:9) lists phases and [`ScanStep`](../controller/workflow/state_machine.py:17) carries coordinates, but neither stores running/paused/completed status, elapsed progress, tube status, or errors.
9. Moonraker access currently exposes only server info, printer info, and G-code POSTs through [`MoonrakerClient`](../controller/network/moonraker.py:18). It does not subscribe to Moonraker's WebSocket, query normalized objects such as toolhead position, or collect Klipper console messages.
10. QR decoding is not wired. [`QrDecodeResult`](../controller/vision/qr_decoder.py:6) defines payload, confidence, and frame ID, but [`QrDecoder.decode()`](../controller/vision/qr_decoder.py:16) always raises.
11. Motion commands refer to `TUBE_PICKUP`, `TUBE_RELEASE`, and `TUBE_SET_YAW` in [`KlipperMotionClient`](../controller/motion/klipper_client.py:10), while the checked-in [`scan.cfg`](../klipper/macros/scan.cfg:1) does not define them. Unknown-command responses must be rendered as errors and collapsed when repeated.

### 3.2 Responsive behavior

- At widths of 900 px and above, use the full layout above with the workflow summary and rack in one card.
- Below 900 px, allow the control bar to wrap; descriptions remain visible beneath labels, not hidden behind hover-only help.
- Below 640 px, show the rack in a horizontally scrollable region with sticky row and column labels. Never shrink 12 columns until cells are untappable.
- The console defaults to 320 px tall on desktop and 260 px on mobile. Its log list scrolls internally; the page must not grow with history.
- Icon-only console controls require visible tooltips, accessible names, keyboard focus, and at least 40 × 40 px hit targets.
- Color is never the sole status signal: every chip/cell uses an icon or text plus color.

### 3.3 Region A: top control bar

Display title, connection chips, workflow state, and normalized toolhead position above five primary actions. Every action has a persistent one-line description on desktop and an accessible tooltip everywhere.

Connection chips:

- **Klipper**: `Ready`, `Startup`, `Shutdown`, `Error`, or `Offline`.
- **Controller**: `Idle`, `Running`, `Paused`, `Stopping`, `Completed`, or `Failed`.
- **Position**: `X`, `Y`, and `Z`, or `Unknown` when Moonraker does not provide valid coordinates.

### 3.4 Region B: workflow visualization

The region combines three levels of detail without exposing the full plan:

1. **Phase stepper**: Home → Approach → Pickup → Scan → Release. Completed phases use a check, the current phase pulses, future phases are muted, and a failed phase uses an error mark. The stepper represents the current tube; Home remains completed after the initial machine home.
2. **Run summary**: current human-readable operation, workflow state chip, QR chip, current rack coordinate, tube progress, step progress, and progress bar. Tube progress is the primary percentage; exact step progress is available in secondary text.
3. **Rack grid**: dimensions derive from settings loaded at [`settings.py:108`](../controller/config/settings.py:108), currently six rows by twelve columns. Cells expose `pending`, `approaching`, `picked_up`, `scanning`, `decoded`, `failed`, `released_without_decode`, `skipped`, or `stopped`. Selecting a cell opens its coordinates, decoded payload, confidence, yaw attempts, error, and timestamps below the grid. Payloads must be text-rendered, never interpreted as HTML.

The grid's final successful status is `decoded`; physical release is represented by `released_at` and current phase rather than replacing decoded status. This preserves the result users care about.

### 3.5 Region C: Klipper-style console

Use a dark card with:

- header title **Console**;
- Clear, Help, Settings, and Collapse icon buttons;
- one-line `Send code...` input and Send button;
- newest-first timestamped event rows in a monospace font;
- visual severity treatment, with errors in red and warnings in amber;
- internal scrolling and bounded history;
- repeat count at the right, such as `6×`;
- optional filters in Settings for severity and source.

The console is for command/response and diagnostic events only. It must not receive one event for every workflow state mutation. Current step, progress, tube status, and QR result belong in Region B. Only notable workflow lifecycle messages—started, paused, resumed, stopped, completed, failed—may appear in the console.

| Control | Disposition | Description or tooltip | Behavior |
|---|---|---|---|
| **Send** | Keep, move into console | `Send the entered G-code to Klipper.` | `POST /api/gcode`; Enter sends, Shift+Enter is not needed because input is single line. Disable blank submissions and while Klipper is offline. |

### 4.3 Remove or demote

- Remove **Refresh Status**. WebSocket snapshots/events replace manual refresh; automatic reconnect invokes a fresh snapshot.
- Remove the standalone **Raw G-code** label and separate Send G-code button. They become the console composer.
- Remove **Workflow Preview** as an always-expanded list. Preview Run populates a concise summary and validation state in Region B.
- Remove raw `<pre>` status output entirely.
- Do not add Reset, Skip Tube, Retry Tube, or Emergency Stop until backend semantics and machine safety behavior exist. Emergency stopping should remain a hardware/Klipper concern unless a separately reviewed endpoint is implemented.

## 5. Backend architecture and transport

### 5.1 Framework and components

Add `aiohttp` as the web/runtime dependency. Keep the existing package boundary, but make the web server asynchronous and split responsibilities:

- `controller/web/server.py`: application factory, route registration, lifecycle startup/cleanup, static/template serving;
- `controller/web/runtime.py`: lock-protected workflow runtime, background task, pause event, stop event, snapshot production;
- `controller/web/events.py`: bounded event store, event classification, repeat collapse, WebSocket fan-out;
- `controller/web/templates/index.html`: document structure;
- `controller/web/static/app.css`: all visual and responsive styling;
- `controller/web/static/app.js`: API client, reconnect logic, state store, rendering, accessibility interactions;
- `controller/workflow/state_machine.py`: plan model and asynchronous/cooperative executor-facing state transitions;
- `controller/network/moonraker.py`: asynchronous Moonraker HTTP and WebSocket client or an async adapter that does not block the event loop;
- `controller/vision/qr_decoder.py`: concrete decoder selection and normalized result/error behavior;
- optionally `controller/vision/camera.py`: camera ownership and frame capture, because no capture component exists today.

The controller should maintain one authoritative runtime snapshot. Mutations occur under an asynchronous lock. A workflow start creates one background task and immediately returns `202 Accepted`; it must never execute the scan in the request coroutine.

### 5.2 Moonraker integration

Use Moonraker's WebSocket API as the upstream source for Klipper notifications and printer object changes, while the browser connects only to the controller WebSocket. The controller should:

1. connect to Moonraker at the WebSocket URL derived from configured [`base_url`](../controller/config/settings.py:76);
2. identify and subscribe to `webhooks`, `toolhead`, `gcode_move`, and `print_stats` where available;
3. normalize `webhooks.state` and `webhooks.state_message` into the status snapshot;
4. normalize `toolhead.position` or `gcode_move.gcode_position` into `machine.position_mm`;
5. convert `notify_gcode_response` text to console events;
6. reconnect with bounded exponential backoff and publish `offline` during disconnect;
7. retain HTTP calls for explicit G-code scripts and server-info/readiness checks.

Do not pass raw Moonraker envelopes through to the browser. Preserve them only in debug logging if needed.

### 5.3 Cooperative workflow behavior

- Check the pause gate and stop flag before every plan step and between QR frame attempts.
- A pause request sets state to `pausing`; after the current Moonraker request completes, transition to `paused`. For simplicity the public contract may expose `paused` only after the gate is reached, while `current.description` says pause requested.
- A stop request transitions immediately to `stopping`. After the active command returns, attempt a configured safe release sequence only if a tube is believed to be held and Klipper remains ready, then move to safe Z if possible. Transition to `stopped` regardless, recording any safe-stop failure as an error.
- Never kill a thread or abandon an in-flight Moonraker HTTP request. The action description must remain honest: Stop is cooperative, not an emergency stop.
- One runtime task may exist at a time. Concurrent start requests return `409 Conflict`.
- QR scanning at each yaw angle captures a frame and invokes the selected decoder. First valid payload marks the tube decoded and allows remaining yaw attempts to be skipped. Exhausting all yaw positions marks `released_without_decode`, then releases the tube and continues unless policy says fail-fast.
- Motion or Moonraker failure marks the active tube failed, performs safe-stop handling, and marks the workflow failed. A QR miss is a tube outcome, not a machine failure.

## 6. API and WebSocket data contract

All timestamps are UTC RFC 3339 strings on the wire, with millisecond precision, for example `2026-08-18T03:36:14.238Z`. The browser formats them in the user's local zone.

### 6.1 HTTP status and errors

- Successful action requests return the action response below.
- Start returns HTTP `202`; successful immediate actions return `200`.
- Invalid JSON or fields return `400`.
- Disallowed state transitions return `409`.
- Klipper unavailable returns `503`.
- Unexpected failures return `500` with a safe message and correlation ID, never a Python traceback.

Error body:

```json
{
  "ok": false,
  "error": {
    "code": "workflow_already_active",
    "message": "A workflow is already running.",
    "correlation_id": "req_01J5..."
  }
}
```

Action response:

```json
{
  "ok": true,
  "action": "workflow.start",
  "accepted_at": "2026-08-18T03:36:14.238Z",
  "workflow_id": "wf_01J5...",
  "message": "Scan queued for 72 tubes."
}
```

### 6.4 Workflow start body

The default starts all tubes. The selection shape allows future retry/partial runs without another API change:

```json
{
  "selection": {
    "mode": "all",
    "tubes": []
  },
  "qr": {
    "continue_on_no_decode": true
  }
}
```

For selected tubes, `mode` is `selected`, and `tubes` contains objects with one-based `row` and `column`. The server validates bounds and removes duplicates.

### 6.5 G-code contract

Request to `POST /api/gcode`:

```json
{
  "script": "G28"
}
```

Response uses the common action response with action `gcode.send`. Limit input to 1,000 characters and reject blank or NUL-containing values. Emit a sanitized command echo as an info console event and the Moonraker/Klipper reply as separate events. Do not put the full Moonraker response into the action response.

### 6.6 Browser WebSocket

Endpoint: `GET /ws` upgraded to WebSocket.

Server-to-client envelope:

```json
{
  "schema_version": 1,
  "sequence": 1843,
  "type": "status.patch",
  "sent_at": "2026-08-18T03:36:14.400Z",
  "payload": {}
}
```

Message types:

| Type | Payload | Rule |
|---|---|---|
| `hello` | `{client_id, heartbeat_seconds, latest_sequence}` | First server message after connection |
| `status.snapshot` | Full status shape from Section 6.2 | Sent immediately after `hello` and after resync |
| `status.patch` | `{controller?, machine?, workflow?, capabilities?, readiness?}` | Shallow replacement by named top-level object; omitted keys are unchanged |
| `tube.updated` | One complete tube object | Replace rack cell keyed by row and column |
| `console.event` | Console event from Section 6.7 | Insert/collapse into console |
| `console.reset` | `{reason, oldest_event_id}` | Tells client its cursor/history is invalid |
| `ping` | `{}` | Application heartbeat if no data has been sent during interval |

Browser-to-server messages are deliberately limited:

```json
{"type": "pong", "sequence": 1843}
```

```json
{"type": "resync", "after_sequence": 1800}
```

All machine-changing actions remain HTTP POSTs so response codes, conflict handling, and CSRF/origin validation are straightforward.

Ordering and recovery:

- `sequence` is monotonically increasing for all server messages in one controller process.
- The browser ignores a sequence it has already applied.
- A gap triggers `resync`; the server responds with `status.snapshot` and console events newer than the client's retained event ID when available.
- On disconnect, display a stale/offline banner, reconnect with exponential backoff capped at 10 seconds, then request a fresh snapshot.
- Validate the WebSocket `Origin` against the configured web origin. Do not expose the service beyond trusted networks without authentication and TLS.

## 7. Console log rules

### 7.1 Classification

Apply the first matching rule:

1. **Error**: Moonraker request failure; HTTP status 400 or above; disconnect after retries; Klipper state `error` or `shutdown`; text containing case-insensitive `error`, `!!`, `unknown command`, `unable`, `failed`, or a Python/controller exception summary.
2. **Warning**: transient reconnect; QR attempts exhausted for one tube; safe-stop degradation; text containing case-insensitive `warning`, `warn`, `not ready`, or `timeout` when the operation can continue.
3. **Debug**: raw subscription details and internal state diagnostics. Hidden by default and disabled in production unless configured.
4. **Info**: command echoes, successful actions, Klipper readiness changes, and workflow lifecycle milestones.

Explicit structured severity from controller code takes precedence over text heuristics. Never classify decoded QR payload text by keywords; payloads are data, not logs.

### 7.2 Timestamp and display

- Store and transmit UTC RFC 3339 timestamps.
- Render with the browser's local time using hour and minute, for example `8:36 PM`; include seconds in the row tooltip and full local date/time in the accessible label.
- When history spans calendar dates, insert date separators such as `Aug 17, 2026`.
- Use browser locale but force a 12-hour display for the requested `h:mm AM/PM` presentation.

### 7.3 Ordering, retention, and clearing

- The visual list is newest first.
- Keep a server-side ring buffer of at most **500 collapsed events**.
- Keep at most **300 rendered rows** in the browser DOM; older rows can remain in the client model only up to the same 500-event cap.
- Initial snapshot/reconnect sends at most the newest **200 collapsed events** after the status snapshot.
- Clear affects one browser only by setting a local event-ID watermark. New events continue to appear. A page reload may restore the watermark from session storage; provide `Show retained history` in Settings to clear it.
- Never persist console events to disk in this release. Document that process restart clears history.

### 7.4 Repeat collapse and deduplication

Collapse an incoming event into the current newest event only when all are true:

- normalized `message`, `level`, `source`, and `command` are identical;
- `correlation_id` is identical, or both correlation IDs are null;
- arrival is within 30 seconds of the newest event's `last_timestamp`;
- no different event was inserted between them.

Normalization trims leading/trailing whitespace, converts CRLF to LF, and collapses repeated spaces outside quoted text. Do not remove numeric values or quoted command names.

On collapse:

- preserve the original `id` and `first_timestamp`;
- update `last_timestamp`, visible `timestamp`, and `repeat_count`;
- emit `console.event` with the same ID as an upsert, not a new row.

Thus six consecutive `Unknown command: TUBE_SET_YAW` events render once with `6×`. A later occurrence after an intervening message or outside the 30-second window creates a new row.

### 7.5 Content boundaries and sanitization

- Workflow step/tube changes travel as `status.patch` or `tube.updated`, not console events.
- Log only lifecycle transitions and actionable anomalies from the workflow.
- Split multiline Klipper responses into separate events sharing a correlation ID unless they are a traceback/controller exception; exception details remain server-side and the UI receives a concise summary.
- Cap a console message at 2,000 characters and append an ellipsis when truncated.
- Render all messages with `textContent`, never `innerHTML`.
- Redact API keys and authorization headers before creating events.

## 8. QR and rack-state requirements

The current decoder interface provides the desired basic result shape but no backend. First release must:

1. add camera capture ownership using configured device and resolution from [`CameraSettings`](../controller/config/settings.py:68);
2. instantiate the configured QR backend from `qr_library`, currently `opencv` in [`camera.json`](../calibration/camera.json:4);
3. return normalized payload, confidence, and frame ID consistent with [`QrDecodeResult`](../controller/vision/qr_decoder.py:6);
4. publish a `tube.updated` event on each transition and update yaw-attempt counters without logging each failed frame;
5. treat an empty/invalid payload as no decode;
6. close camera resources on server cleanup and after unrecoverable capture failure;
7. expose `capabilities.qr = false` and a readiness issue when OpenCV/camera initialization fails;
8. never include full frames or images in status/WebSocket payloads in this release.

Suggested readiness issues include `moonraker_offline`, `klipper_not_ready`, `axes_not_homed`, `missing_klipper_macro`, `camera_unavailable`, and `qr_backend_unavailable`.

## 9. Static/template file organization

Recommended tree:

```text
controller/web/
├── __init__.py
├── server.py
├── runtime.py
├── events.py
├── templates/
│   └── index.html
└── static/
    ├── app.css
    └── app.js
```

Serving behavior:

- Register `/` to return `templates/index.html` with `aiohttp.web.FileResponse`; no template engine is needed because the browser obtains all runtime data from `/api/status`.
- Register `/static/` with `aiohttp.web.static` rooted at `controller/web/static`.
- Resolve both paths relative to `Path(__file__).parent`, never the process working directory.
- Set `Content-Type` through the framework and `Cache-Control: no-cache` for `index.html` during development. Static assets may use `no-cache` initially; content hashing can be added later.
- Keep API and WebSocket routes ahead of any static route and do not expose directory listings.
- Add static/template files as setuptools package data in [`pyproject.toml`](../pyproject.toml:14), otherwise installed console-script deployments may omit them.
- Keep inline SVG icons in the HTML or draw them with CSS; do not add an icon library solely for four controls.

This split removes presentation concerns from [`server.py`](../controller/web/server.py), makes browser code testable, and avoids Python f-string escaping throughout CSS and JavaScript.

## 10. Safety, concurrency, and accessibility acceptance rules

- The backend, not only the UI, rejects unsafe or conflicting actions.
- Home and arbitrary G-code cannot run concurrently with a workflow.
- Pause/Resume/Stop requests are idempotent where practical; repeated Stop while stopping returns the current accepted state.
- A held-tube flag is explicit runtime state and drives safe-stop release behavior.
- All background task exceptions are observed, classified, correlated, and reflected in workflow state.
- Browser controls use native buttons and inputs; rack cells are keyboard-focusable buttons with row/column/status accessible names.
- Focus returns to the invoking control after closing dialogs/popovers.
- A live region announces only major changes: started, paused, resumed, stopped, completed, failed, and decoded/failed current tube. It must not announce every position update.
- Respect reduced-motion preferences; pulsing active indicators become static outlines.
- Minimum contrast meets WCAG AA. Error red is paired with an error icon/text.
